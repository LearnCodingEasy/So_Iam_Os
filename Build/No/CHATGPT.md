# 1. القاعدة الأساسية: Preserve First, Extend Second

هذه هي القاعدة الأهم في المشروع بالكامل.

1. حافظ على جميع المميزات والوظائف الموجودة حاليًا.
2. لا تعِد بناء المشروع من الصفر.
3. لا تحذف أي تطبيق أو ملف أو API أو Model أو View أو URL أو مكون Frontend قائم لمجرد أن لديك تصميمًا بديلًا.
4. لا تستبدل ملفات كاملة دون فهم محتواها واستخداماتها وتأثير التغيير على بقية المشروع.
5. وسّع البنية الحالية بأقل تغييرات ممكنة، مع إعادة استخدام المكونات والخدمات الموجودة.
6. حافظ على توافق التغييرات الجديدة مع البيانات الحالية وقاعدة البيانات وإعدادات التشغيل.
7. لا تستخدم Mock Data أو Fake APIs لإيهام المستخدم بأن الوظائف تعمل.
8. لا تدّعِ نجاح أي ميزة أو اختبار لم يتم تنفيذه والتحقق من نتيجته فعليًا.
9. لا تكتب ملفات مكررة إذا كانت هناك ملفات أو خدمات تؤدي الوظيفة نفسها.
10. لا تنفذ تغييرات مدمرة في قاعدة البيانات أو إعدادات الأمان دون ضرورة واضحة وخطة آمنة.

قبل أي تعديل، افحص حالة Git إن كانت متاحة، وسجّل التغييرات الموجودة مسبقًا. لا تتخلص من تعديلات المستخدم ولا تستبدلها دون إذن.

| العنصر | المطلوب |

# 4. المرحلة الثانية: إعادة تنظيم AI Backend

راجع تطبيق `ai` الحالي، وحسّن تنظيمه دون كسر واجهاته الحالية أو إزالة وظائفه.

## 4.1 تنظيم الخدمات

أضف مجلد `services/` داخل تطبيق AI إذا كان مناسبًا للبنية الحالية ولم يكن موجودًا بالفعل.

مثال استرشادي فقط:

```text
backend_django/
└── ai/
    ├── __init__.py
    ├── models.py
    ├── serializers.py
    ├── views.py
    ├── urls.py
    ├── exceptions.py
    ├── prompts.py
    ├── providers.py
    ├── permissions.py
    ├── tasks.py
    ├── services/
    │   ├── __init__.py
    │   ├── learning_actions.py
    │   ├── agent_selector.py
    │   ├── agent_executor.py
    │   ├── provider_manager.py
    │   ├── fallback_service.py
    │   ├── conversation_service.py
    │   ├── context_inspector.py
    │   ├── prompt_template_service.py
    │   ├── task_planner.py
    │   ├── knowledge_service.py
    │   ├── usage_service.py
    │   └── workflow_service.py
    └── tests/
```

عدّل الأسماء والتقسيم وفق الكود الموجود بالفعل. لا تنشئ وحدات مستقلة لمجرد استكمال العدد.

## 4.2 إنشاء 10 وحدات خدمات جديدة

أريد إنشاء **10 ملفات خدمة جديدة على الأقل**، مستوحاة من أسلوب وتنظيم `learning_actions.py` الموجود بالمشروع.

قبل إنشائها:

1. اقرأ `learning_actions.py` بالكامل.
2. افهم أسلوب معالجة الأخطاء، واستدعاء الخدمات، والتعامل مع Models.
3. افحص الخدمات الموجودة لتجنب التكرار.
4. استخدم أسماء تتوافق مع أسلوب التسمية في المشروع.

يجب أن تغطي الخدمات وظائف فعلية مثل:

1. اختيار Agent المناسب للسياق.
2. تنفيذ الوكلاء وتنسيق نتائجهم.
3. إدارة مزودي النماذج.
4. تنفيذ سلسلة Fallback.
5. إدارة المحادثات وسجلها.
6. فحص السياق والبيانات المعرفية.
7. إدارة قوالب Prompts.
8. تحويل المحادثات إلى مهام.
9. تتبع استهلاك التوكنز والتكلفة والميزانية.
10. تنسيق Workflows متعددة الوكلاء.

إذا كانت هناك حاجة إلى خدمة إضافية مثل إدارة الصلاحيات أو المراجع، فأضفها عندما تكون مبررة.

لكل خدمة:

- واجهة استخدام واضحة.
- مسؤولية محددة.
- Type hints مناسبة.
- معالجة أخطاء متسقة.
- Logging منظم.
- اختبارات.
- تكامل حقيقي مع Django Models والخدمات ذات الصلة.
- عدم تضمين أسرار أو مفاتيح API داخل الكود.

لا تجعل الملفات مجرد Wrappers فارغة أو دوال شكلية لا تنفذ منطقًا فعليًا.

## 4.3 تنظيم ملفات AI الأساسية

راجع الملفات التالية:

- `exceptions.py`
- `prompts.py`
- `providers.py`

إذا كانت موجودة داخل أماكن مختلفة، فانقلها إلى هيكل موحد فقط عندما يكون ذلك ضروريًا ومناسبًا.

أثناء النقل:

- حدّث جميع Imports.
- حافظ على التوافق مع الكود القديم.
- تجنب Circular Imports.
- حافظ على أسماء الواجهات العامة المستخدمة حاليًا.
- استخدم Re-export أو طبقة توافق مؤقتة عند الحاجة.
- حدّث الاختبارات والإعدادات وأي Celery tasks متأثرة.

لا تنقل هذه الملفات بصورة عشوائية، ولا تكرر تعريفات Models أو إعدادات المزودين.

# 5. المرحلة الثالثة: تنفيذ مميزات AI المطلوبة

نفّذ المميزات الخمس عشرة التالية بصورة متكاملة بين Backend وFrontend.

## 5.1 Dynamic Agent Selector

أنشئ نظامًا لاختيار Agent مناسب حسب:

- رسالة المستخدم.
- سياق المحادثة.
- نوع المهمة.
- التطبيقات والموارد المرتبطة.
- صلاحيات المستخدم.
- القدرات المتاحة للوكلاء.
- تكلفة التنفيذ والميزانية.

يجب أن يكون الاختيار واضحًا وقابلًا للتفسير والتسجيل، مع وجود Agent افتراضي أو مسار آمن عند عدم توفر Agent مناسب.

لا تسمح للسياق وحده بتجاوز الصلاحيات.

## 5.2 Agent Execution Monitor

أنشئ لوحة مراقبة لعمليات التنفيذ تعرض:

- حالة التنفيذ.
- Agent المستخدم.
- وقت البداية والنهاية.
- المدة.
- عدد التوكنز عند توفره.
- التكلفة التقديرية.
- الأخطاء وإعادة المحاولة.
- حالة مهام Celery.

استخدم Django وCelery وواجهات مراقبة مناسبة للبنية الحالية.

استخدم WebSocket أو SSE للتحديث المباشر إذا كانت البيئة تدعمهما، وإلا استخدم Polling مضبوطًا مع معالجة انقطاع الاتصال.

لا تدّعِ أن النظام Live إذا كانت البيانات لا تتحدث فعليًا.

## 5.3 AI Provider Switcher UI

ادعم المزودين المطلوبين حسب توافقهم مع التنفيذ الفعلي:

- OpenAI
- Gemini
- Ollama
- DeepSeek
- مزودين إضافيين عند الحاجة.

وفّر واجهة لإدارة المزود الافتراضي، والنماذج، واختبار الاتصال، وعرض حالة المزود، واختيار المزود لكل مهمة عندما يكون ذلك مسموحًا.

يجب فصل إعدادات المزودين عن منطق الوكلاء.

لا تعرض مفاتيح API بعد حفظها، ولا ترسلها إلى Frontend مرة أخرى. استخدم تخزينًا آمنًا على Backend، مع صلاحيات وصول مناسبة، وإمكانية استبدال المفتاح أو حذفه، ورسائل واضحة لحالة الاتصال.

لا تسمح بتغيير إعدادات عامة حساسة لمستخدم لا يمتلك الصلاحية المناسبة.

## 5.4 Persistent Chat History

أنشئ نظامًا لحفظ المحادثات والرسائل مع:

- ربطها بالمستخدم.
- عناوين قابلة للتعديل.
- ترتيب زمني.
- Pagination.
- بحث متقدم.
- فلترة حسب التاريخ والمزود وAgent.
- حذف أو أرشفة حسب سياسة المشروع.
- استعادة المحادثة واستكمالها.

طبّق عزلًا صارمًا للبيانات بحيث لا يستطيع المستخدم قراءة محادثات مستخدم آخر.

## 5.5 Context Inspector

أنشئ أداة لفحص السياق الذي تم إرساله إلى النموذج، تشمل عند السماح:

- الرسائل ذات الصلة.
- التعليمات المستخدمة.
- مصادر Knowledge المسترجعة.
- ملخص الذاكرة المستخدم.
- البيانات التي أُضيفت إلى الطلب.
- عدد التوكنز أو التقدير المتاح.

افصل بين السياق الفعلي المرسل للنموذج والسياق المحتمل أو الملخص.

احجب كلمات المرور والمفاتيح والبيانات الحساسة. لا تعرض System Prompts أو بيانات داخلية سرية إلا عندما تكون هناك سياسة صريحة تسمح بذلك.

## 5.6 Reusable Prompt Templates

أنشئ مكتبة لقوالب Prompts تتيح:

- الإنشاء والتعديل والحفظ.
- النسخ والاستخدام بنقرة واحدة.
- التصنيف والبحث.
- المتغيرات الديناميكية.
- التحقق من المتغيرات المطلوبة.
- قوالب خاصة بالمستخدم وأخرى عامة حسب الصلاحيات.

لا تسمح باستخدام قالب محفوظ لتجاوز سياسات الأمان.

## 5.7 AI Task Planner

حوّل طلبات المستخدم إلى مهام منظمة قابلة للمراجعة، مثل:

- عنوان المهمة.
- الوصف.
- الأولوية.
- الموعد النهائي.
- الخطوات الفرعية.
- الاعتماديات.
- التطبيق المسؤول عن التنفيذ.

اربط الميزة بتطبيق `tasks` الفعلي.

اعرض المهام المقترحة للمستخدم، واطلب تأكيده قبل إنشاء المهام أو تنفيذ عمليات لها أثر خارجي، ما لم تكن هناك آلية موافقة مسبقة واضحة.

## 5.8 Tool Permissions Manager

أنشئ نظام صلاحيات للأدوات والوكلاء، يحدد:

- الأدوات المسموح بها.
- العمليات المسموحة على كل تطبيق.
- صلاحيات القراءة والكتابة والتعديل والحذف.
- حدود الموارد.
- العمليات التي تحتاج إلى تأكيد.
- سجل منح الصلاحيات وتغييرها.

استخدم Django permissions والسياسات الحالية قدر الإمكان.

يجب أن يتحقق Backend من الصلاحيات في كل طلب وكل عملية، وليس في الواجهة فقط.

لا تمنح Agent وصولًا عامًا إلى قاعدة البيانات أو تنفيذ SQL اعتباطي.

## 5.9 Citation & Source Inspector

اربط إجابات AI بتطبيق `knowledge` الفعلي.

اعرض:

- المصدر.
- المقطع المسترجع.
- عنوان الوثيقة.
- الرابط أو المعرّف عند توفره.
- درجة الصلة إذا كانت متاحة.
- العلاقة بين المصدر والجزء الذي يدعمه من الإجابة.

لا تختلق مراجع أو روابط أو درجات ثقة غير موجودة في نتائج الاسترجاع.

## 5.10 Agent Audit & History Log

سجّل عمليات الوكلاء، بما يشمل:

- المستخدم.
- Agent.
- المهمة.
- وقت التنفيذ.
- المزود والنموذج.
- النتيجة أو الحالة.
- الأخطاء.
- العمليات التي تم استدعاؤها.
- المدة والتكلفة المتاحة.
- الموافقات المتعلقة بالتنفيذ.

يجب أن يكون سجل التدقيق محميًا من التعديل غير المصرح به، مع صلاحيات مناسبة للاطلاع والاحتفاظ بالبيانات.

لا تسجل الأسرار أو مفاتيح API أو المحتوى الحساس بصورة مكشوفة.

## 5.11 Multi-Model Comparison View

أنشئ واجهة تسمح بإرسال السؤال نفسه إلى أكثر من نموذج وعرض النتائج جنبًا إلى جنب.

اعرض:

- المزود والنموذج.
- الإجابة.
- وقت الاستجابة.
- استهلاك التوكنز عند توفره.
- التكلفة التقديرية.
- الأخطاء.

استخدم تنفيذًا متوازيًا مضبوطًا، مع حدود زمنية واستهلاك موارد واضح.

تحقق من صلاحية المستخدم وميزانيته قبل تشغيل عدة نماذج.

## 5.12 AI Usage & Token Dashboard

أنشئ لوحة تعرض:

- إجمالي الاستخدام.
- استهلاك التوكنز.
- التكلفة التقديرية.
- الاستهلاك حسب المزود والنموذج.
- الاستهلاك حسب المستخدم أو Agent.
- الاتجاهات اليومية والشهرية.

ميّز بين القيم الفعلية التي يقدمها المزود والقيم المقدرة.

استخدم أسعارًا قابلة للتحديث، ولا تفترض أن جميع النماذج تتبع تسعيرًا واحدًا.

## 5.13 Budget & Rate Limiting Controls

أضف حدودًا للاستخدام على مستويات:

- المستخدم.
- Agent.
- المزود.
- اليوم.
- الشهر.

استخدم معاملات آمنة وعمليات ذرية أو آلية تنسيق مناسبة لمنع تجاوز الحدود عند وجود طلبات متزامنة.

عند تجاوز الميزانية، أوقف التنفيذ أو انتقل إلى بديل مسموح به وفق السياسة، مع توضيح السبب.

لا تسمح بتجاوز حدود الميزانية عن طريق إعادة المحاولة أو تبديل المزود.

## 5.14 Answer Feedback System

أضف إمكانية تقييم الإجابات:

- إعجاب.
- عدم إعجاب.
- تعليق اختياري.
- سبب التقييم عند الحاجة.
- ربط التقييم بالمحادثة والإجابة والموديل.

وفّر تقارير لتحليل جودة الإجابات.

لا تستخدم التعليقات لتعديل سلوك النموذج تلقائيًا أو لتغيير Prompts العامة دون مراجعة وسياسة واضحة.

## 5.15 AI Workflow Builder

أنشئ Visual Workflow Builder باستخدام Vue Flow الموجود بالفعل.

يجب أن يدعم:

- إنشاء العقد وتوصيلها.
- تحديد ترتيب التنفيذ.
- تعريف المدخلات والمخرجات.
- الشروط والتفرعات.
- تمرير البيانات بين العقد.
- التحقق من صحة المسار.
- حفظ المخططات وإعادة فتحها.
- تنفيذ المسارات ومراقبة حالتها.
- عرض الأخطاء والنتائج.

استخدم Backend للتحقق من المخطط وتنفيذ الـ Workflow. لا تجعل المتصفح هو الجهة الموثوقة الوحيدة التي تقرر ما يجوز تنفيذه.

ضع حدودًا للعمق والوقت والموارد وعدد العقد. امنع الحلقات غير المسموح بها، ونفّذ عمليات الإيقاف والإلغاء عند دعم البنية لذلك.

# 6. المرحلة الرابعة: نظام Fallback Chain متعدد المزودين

أنشئ نظام Fallback Chain فعليًا.

مثال توضيحي:

```text
Primary Provider
       |
       v
Check Availability
       |
       +---- Success ----> Return Response
       |
       v
Classify Error
       |
       v
Try Approved Fallback
       |
       +---- Success ----> Return Response
       |
       v
Next Approved Provider
       |
       v
All Attempts Failed
       |
       v
Return Structured Error
```

## متطلبات التنفيذ

1. تحديد المزود والنموذج الأساسيين.
2. تعريف قائمة بدائل مرتبة لكل مستخدم أو Agent أو نوع مهمة.
3. فحص توافر المزود وإمكانية استخدام النموذج.
4. التبديل عند الأخطاء المؤهلة، مثل تعطل الخدمة أو تجاوز المهلة أو بعض أخطاء Rate Limit.
5. عدم إعادة المحاولة تلقائيًا عند أخطاء التحقق أو الصلاحيات أو الطلبات غير الصالحة.
6. التعامل مع أخطاء المصادقة وفق سياسة واضحة؛ لا تعتبر كل أخطاء API قابلة للإصلاح بمجرد تبديل المزود.
7. تطبيق Timeouts وRetry Limits وBackoff مناسب.
8. عدم تكرار العمليات ذات الآثار الجانبية دون Idempotency أو ضمان مناسب.
9. احترام ميزانية المستخدم والحدود المسموح بها لجميع المزودين.
10. تسجيل كل محاولة وسبب التبديل والنتيجة.
11. إرجاع استجابة متوافقة مع الواجهة الحالية قدر الإمكان.
12. عدم كشف التفاصيل الداخلية أو الأسرار في رسائل الخطأ.
13. توفير اختبارات تغطي نجاح المزود الأساسي، وفشله، ونجاح البديل، وفشل جميع المزودين.

إذا كانت الاستجابة قد بدأت في البث المباشر إلى المستخدم، فلا تحاول تبديل المزود بطريقة تؤدي إلى تكرار أجزاء الإجابة أو إفساد الـ Stream. استخدم سياسة واضحة لإعادة التشغيل أو أوقف المحاولة وأبلغ المستخدم بصورة مناسبة.

يجب أن يكون Fallback Chain قابلًا للتهيئة والاختبار، وليس سلسلة ثابتة مخفية داخل الكود.

# 7. المرحلة الخامسة: ربط Frontend وBackend بالكامل

الهدف هو أن تصبح وظائف المشروع الحقيقية متاحة من الواجهة، مع الحفاظ على المعمارية الحالية.

## 7.1 Backend API

راجع كل تطبيق من التطبيقات الفعلية، وليس تطبيق AI فقط.

لكل تطبيق، افحص:

- Models.
- Serializers.
- Views.
- URLs.
- Services.
- Permissions.
- Authentication.
- Validation.
- Tests.

أضف أو استكمل API endpoints اللازمة فقط.

لكل Endpoint، تأكد من وجود:

- HTTP method مناسب.
- Serializer أو Validation مناسبة.
- Authentication عند الحاجة.
- Authorization.
- معالجة للأخطاء.
- Response schema واضح.
- Pagination أو Filtering عندما تكون مطلوبة.
- اختبارات.

حافظ على مسارات API القديمة، وأضف مسارات جديدة بصورة متوافقة قدر الإمكان.

لا تنشئ Endpoint وهميًا يعيد بيانات ثابتة بدلًا من تنفيذ الوظيفة الحقيقية.

## 7.2 Frontend API Services

استخدم Axios الموجود بالفعل، وأنشئ أو حدّث طبقة خدمات واضحة.

```text
├── conversationService.js

├── taskPlannerService.js
├── usageService.js

└── workflowService.js
```

عدّل هذا الهيكل وفق الملفات الموجودة بالفعل، ولا تكرر خدمات قائمة.

يجب أن تتعامل الخدمات مع:

- Base URL من إعدادات البيئة.
- Authentication headers وفق نظام المشروع.
- Timeout.
- Error normalization.
- Pagination.
- Uploads عند الحاجة.
- التعامل مع انتهاء الجلسة.
- إلغاء الطلبات عند الحاجة.
- أنواع البيانات المتوقعة.

لا تضع مفاتيح API الخاصة بمزودي الذكاء الاصطناعي في Frontend أو ملفات Vite العامة.

## 7.3 Pinia

استخدم Pinia لإدارة الحالة المشتركة، مثل:

- المحادثات.
- المزود الحالي.
- حالة الاتصال.
- الوكلاء.
- حالة تنفيذ المهام.
- استهلاك الموارد.
- قوالب Prompts.
- الـ Workflows.

افصل حالة الواجهة عن منطق طلبات API وعن منطق الأعمال.

تجنب تخزين البيانات الحساسة داخل Local Storage أو Session Storage دون ضرورة وسياسة حماية واضحة.

## 7.4 Vue Router

راجع المسارات الحالية وأضف صفحات المميزات الجديدة مع الحفاظ على المسارات القديمة.

استخدم:

- Route names واضحة.
- Guards متوافقة مع Authentication.
- صلاحيات الوصول للصفحات.
- Lazy loading عند ملاءمته.
- معالجة المسارات غير الموجودة.

لا تعتبر إخفاء الصفحة في Router بديلًا عن حماية Backend.

## 7.5 اختبار الاتصال

لكل ميزة، تحقق من الدورة الكاملة:

```text
Vue Component
    ↓
Pinia Store
    ↓
Axios Service
    ↓
Django URL
    ↓
View / API Layer
    ↓
Serializer / Validation
    ↓
Business Service
    ↓
Database / AI Provider / Celery
    ↓
API Response
    ↓
Pinia State Update
    ↓
Vue UI Update
```

لا تكتفِ بوجود الملفات. تحقق من أن كل خطوة مرتبطة بالفعل بما يليها.

# 14. المرحلة الأخيرة: تقرير التغييرات وتسليم المشروع

بعد التنفيذ، أنشئ تقريرًا نهائيًا واضحًا باللغة العربية.

## القسم الأول: ملخص التنفيذ

اذكر ما تم تنفيذه فعليًا، وما تم تحسينه، وما بقي دون تنفيذ، وأسباب ذلك.

## القسم الثاني: قائمة الملفات المعدلة

استخدم جدولًا بالشكل التالي:

| الملف | المسار الكامل | نوع التغيير | السبب |
|---|---|---|---|
| مثال توضيحي | المسار الفعلي | تعديل / إنشاء / نقل | سبب التغيير |

يجب أن تشمل القائمة جميع الملفات التي أُنشئت أو عُدّلت أو نُقلت، وليس ملفات AI فقط.

أضف قائمة منفصلة بالملفات المحذوفة إن حدث حذف مبرر ومصرح به، وإلا وضح أنه لم يتم حذف ملفات.

## القسم الثالث: API Endpoints

لكل Endpoint جديد أو معدل، اذكر:

- HTTP Method.
- المسار الفعلي.
- الوظيفة.
- الصلاحيات.
- Serializer المستخدم.
- الصفحة أو الخدمة التي تتصل به.
- نتيجة الاختبار.

## القسم الرابع: قاعدة البيانات

اذكر:

- Models الجديدة أو المعدلة.
- Migrations التي أُنشئت.
- ما إذا تم تطبيقها.
- أي إعدادات مطلوبة لتشغيلها.

## القسم الخامس: الاختبارات

أنشئ جدولًا يوضح:

| الاختبار | الأمر المنفذ | النتيجة | ملاحظات |
|---|---|---|---|

ميّز بين Passed وFailed وBlocked وNot Run.

لا تستخدم نتيجة Passed إذا لم يتم تنفيذ الاختبار.

## القسم السادس: التشغيل

وثّق أوامر تشغيل Backend وFrontend وCelery وأي خدمات إضافية يحتاج إليها المشروع.

اذكر متغيرات البيئة المطلوبة دون كشف قيم الأسرار.

## القسم السابع: المشكلات المتبقية

اذكر الأخطاء أو المتطلبات الخارجية أو القيود التي تمنع الوصول إلى جاهزية الإنتاج.

## القسم الثامن: ملف ZIP النهائي

أنشئ ملف ZIP يحتوي على **المشروع كاملًا بعد التحديث**، وليس مجموعة من الملفات المعدلة فقط.

المتطلبات:

- تضمين ملفات Backend وFrontend والمكونات الضرورية للمشروع.
- تضمين ملفات الإعداد والتوثيق المطلوبة.
- تضمين Migrations والاختبارات والملفات الجديدة.
- عدم حذف ملفات المستخدم الأصلية المطلوبة.
- عدم تضمين `.env` أو مفاتيح API أو الأسرار.
- عدم تضمين مجلدات ضخمة أو مؤقتة مثل `node_modules` وبيئات Python الافتراضية وملفات Cache، إلا إذا كان هناك سبب محدد.
- عدم استبدال قاعدة البيانات الأصلية دون إذن.
- الاحتفاظ بنسخة المستخدم الأصلية وعدم تعديلها بطريقة مدمرة.
- التأكد من إمكانية فتح ملف ZIP وفحص محتوياته.
- التأكد من وجود ملفات المشروع الأساسية داخله.

سمِّ الملف مثلًا:

`SO_IAM_OS_updated.zip`

إذا كانت بيئة العمل تسمح بإنشاء ملفات وتسليمها، أرفق رابطًا مباشرًا للنسخة الكاملة.

# 15. طريقة العمل الإلزامية

نفّذ العمل وفق الترتيب التالي:

1. استكشاف الملفات والبنية الفعلية.
2. قراءة الملفات الأساسية وفهم العلاقات بينها.
3. إعداد خريطة التطبيقات والـ APIs والـ Frontend.
4. تحديد المخاطر والتبعيات والخطة التنفيذية.
5. تنفيذ تحسينات Backend وAI.
6. تنفيذ Models وSerializers وViews وURLs وServices اللازمة.
7. تنفيذ Frontend Services وPinia Stores والصفحات والمكونات.
8. ربط التطبيقات ببعضها والتحقق من الصلاحيات.
9. تنفيذ Fallback Chain.
10. إنشاء Migrations عند الحاجة.
11. تشغيل اختبارات Backend.
12. تشغيل اختبارات Frontend.
13. تنفيذ اختبارات التكامل وإصلاح الأخطاء.
14. مراجعة التغييرات النهائية والتأكد من عدم فقدان المميزات القديمة.
15. إنشاء التقرير النهائي ونسخة ZIP الكاملة.

يمكن تقسيم التنفيذ إلى مراحل داخلية لتسهيل العمل، لكن لا تتوقف بعد كل مرحلة لطلب موافقة على الخطوة التالية ما لم توجد مخاطرة حقيقية أو عملية مدمرة تحتاج إلى إذن.

إذا كانت بعض المتطلبات كبيرة بالنسبة إلى جلسة واحدة، فأنجز أكبر قدر ممكن من العمل الفعلي، ورتّب الأولويات حسب الاعتماديات والأمان، ووثّق بدقة ما اكتمل وما بقي.

**ابدأ الآن بفحص المشروع الموجود فعليًا، وليس بإنشاء مشروع جديد أو كتابة كود افتراضي. بعد الفحص، نفّذ التطوير داخل الملفات الحقيقية، واختبره، وسلّم التقرير والنسخة الكاملة المحدثة.**


16. CHANGELOG — تقرير جميع التغييرات داخل المشروع
يجب إنشاء تقرير هندسي شامل يوثّق كل تغيير تم إجراؤه في المشروع، سواء في Backend أو Frontend أو قاعدة البيانات أو خدمات الذكاء الاصطناعي.

ممنوع الاكتفاء بذكر أسماء المميزات. يجب تحديد الملفات والمسارات الفعلية والتغييرات التي حدثت داخل كل ملف.
16.1 قائمة الملفات التي تم تعديلها أو إنشاؤها
أنشئ جدولًا شاملًا:
#	اسم الملف	المسار الكامل داخل المشروع	نوع التغيير	تفاصيل التغيير
1	agent_selector.py	backend_django/ai/services/agent_selector.py	إنشاء	إنشاء نظام اختيار الوكيل المناسب
2	providers.py	backend_django/ai/providers.py	تعديل	تحسين إدارة مزودي AI
3	aiService.js	frontend_vue/src/services/aiService.js	تعديل	ربط الواجهة بخدمات Backend
4	AIProviderView.vue	frontend_vue/src/views/AIProviderView.vue	إنشاء	واجهة إدارة المزودين

هذه أمثلة توضيحية فقط. يجب استخراج القائمة من التغييرات الفعلية.

صنّف الملفات إلى:
- ملفات جديدة (Created).
- ملفات معدلة (Modified).
- ملفات تم نقلها (Moved).
- ملفات تم حذفها (Deleted).
- ملفات لم يتم تغييرها رغم فحصها.
16.2 شرح التغييرات داخل كل ملف
لكل ملف تم إنشاؤه أو تعديله، اشرح:
1. ما وظيفة الملف؟
2. ما المشكلة التي كانت موجودة؟
3. ما الذي تغير تحديدًا؟
4. ما الدوال أو الكلاسات الجديدة؟
5. ما الدوال أو الكلاسات التي تم تعديلها؟
6. ما الملفات الأخرى التي أصبحت تعتمد عليه؟
7. ما الخدمات أو التطبيقات التي يتصل بها؟
8. ما تأثير التغيير على وظائف المشروع القديمة؟
9. كيف تم اختبار التغيير؟
16.3 تحديد المسارات والارتباطات بين الملفات
يجب توضيح المسار الكامل لكل ملف، وكيفية ارتباطه ببقية المشروع.

حدد أيضًا أي مخاطر أو تغييرات قد تؤثر على أجزاء أخرى من المشروع.
16.6 تقرير الملفات المرتبطة والتبعيات
لكل ملف جديد أو معدل، اذكر:
- الملفات التي يستورد منها.
- الملفات التي تستورده.
- الخدمات التي يستدعيها.
- Models التي يتعامل معها.
- APIs التي يستخدمها.
- الصفحات أو المكونات التي تعتمد عليه.
الهدف هو معرفة تأثير حذف أو تعديل أي ملف مستقبلًا.
16.7 تقرير API Changes

16.8 تقرير قاعدة البيانات

- Models الجديدة.
- Models المعدلة.
- الحقول الجديدة.
- العلاقات الجديدة.
- الفهارس والقيود.
- ملفات Migrations.
- التغييرات التي تم تطبيقها.
- توافق التغييرات مع البيانات القديمة.
16.9 تقرير الحفاظ على المشروع الأصلي
يجب تقديم إثبات واضح لما يلي:
- الوظائف القديمة التي تم الحفاظ عليها.
- الملفات التي لم يتم المساس بها.
- الملفات التي تغير سلوكها.
- أي وظائف تم إيقافها أو استبدالها.
- أي تغييرات تتطلب تعديل إعدادات التشغيل.
لا تحذف أو تستبدل أي وظيفة موجودة دون توثيق السبب.
